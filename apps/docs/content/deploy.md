# Deploying to a server

Nothing in Tollgate requires `127.0.0.1`. That address is only the default, chosen so that a fresh install is reachable from your own computer and nowhere else. This page covers running it anywhere else: a home server, a virtual machine, a container host.

## The pieces and where each may live

| Piece | What it is | Where it may run |
| --- | --- | --- |
| **Gateway** | The only thing an agent, the dashboard and the phone talk to. Node 22, Hono. | Anywhere you can reach over the network. Binds the address in `GATEWAY_HOST` (default `127.0.0.1`) and the port in `PORT` (default `8787`). |
| **Signer** | Holds the only key. | **Next to the gateway, on the same machine or container.** It always listens on `127.0.0.1:SIGNER_PORT`; that is fixed in code so the key can never be reached from the network. |
| **Database** | Postgres. Holds every mandate, decision, ledger entry and audit entry. | Anywhere the gateway can reach. A hosted Postgres is fine. |
| **Agent host** | The program that answers hosted chat agents using a model you choose. | Started by `pnpm live:app` on your own computer. |
| **Reference services** | `apps/workers`: the demo merchant, seller and worker. | Optional. Anywhere with the 1Click key. |

```
   agents, phone, dashboard                      one host (a machine, VM or container)
   ───────────────────────►  https://gateway.example.com
                                      │  reverse proxy: terminates https
                                      ▼
                          ┌───────────────────────────────┐
                          │ gateway   0.0.0.0:PORT        │ ──► Postgres (DATABASE_URL, anywhere)
                          │    │                          │
                          │    ▼  http://127.0.0.1:8788   │
                          │ signer    127.0.0.1 only      │
                          └───────────────────────────────┘
```

### Why the signer is not separately reachable

A signer on its own public address would put the only key on the internet. Keeping it on loopback beside the gateway means it can be asked only by a process on the same machine, and it still requires the service token. If you want it on a different machine, you must provide your own private tunnel between the two. Tollgate does not ship one, and does not support exposing the signer port.

## What you set

These are the settings that change when you leave your laptop. The full list is in [Configuration](/configuration/).

| Setting | Laptop default | On a server |
| --- | --- | --- |
| `GATEWAY_HOST` | `127.0.0.1` (this computer only) | `0.0.0.0` so the network can reach it. The gateway prints a warning when you do, because every call still needs a token and you must put https in front. |
| `PORT` | `8787` | Whatever your host gives you. Many hosts set `PORT` for you. |
| `GATEWAY_OPERATOR_TOKEN` | generated by `pnpm onboard` | A long random value (at least 16 characters). This is the owner's password: the dashboard and the phone use it. Set it as a secret, never in a file you commit. |
| `DATABASE_URL` | local Docker Postgres | Your hosted Postgres, for example `postgres://USER:PASSWORD@HOST:5432/DBNAME`. |
| `DATABASE_POOL_MAX` | `10` | Keep it under your plan's connection limit. Small hosted plans allow few connections, and several processes sharing one database add up. |
| `SIGNER_URL` | `http://127.0.0.1:8788` | The same, `http://127.0.0.1:` and the signer's port, because the signer is beside the gateway. |
| `SIGNER_SERVICE_TOKEN` | generated | At least 32 characters, shared by gateway and signer. |
| `SIGNER_KEY_FILE` | set by `pnpm onboard` | A path to a key file with mode `600`. The signer refuses a key that other users can read. |
| `TOLLGATE_OFFLINE` | `true` (recorded answers, no funds) | `false` for live payments, which also needs `NEAR_1CLICK_API_KEY`. |

The gateway checks its settings when it starts and says exactly which one is wrong, then exits.

## Put https in front

The gateway speaks plain HTTP. For anything beyond a network you trust, run a reverse proxy that terminates https. With Caddy, which obtains and renews certificates itself:

```
gateway.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

Then:

- The phone app accepts `https://` anywhere. Plain `http://` is accepted only for `localhost`, a private network address, or a `.local` name, so a real deployment needs https for the phone to pair.
- The dashboard is served by the gateway at `https://gateway.example.com/dashboard`.
- Health checks use `GET /healthz`, which needs no key.

## Run it

Install, then start the signer and the gateway together in one service:

```bash
pnpm install --frozen-lockfile
node scripts/start-hosted.mjs        # signer on 127.0.0.1, gateway on GATEWAY_HOST:PORT
```

`scripts/start-hosted.mjs` starts both and stops both if either one exits, so a supervisor restarts them cleanly. The repository's `render.yaml` is a worked example of this for a managed host; the same shape works on any host that can run Node 22 and holds secrets as environment variables or secret files.

On first start the gateway creates its own tables in the database and upgrades them as versions change. Nothing else needs to be run.

## Pair the phone with a deployed gateway

1. Open the dashboard at your gateway's https address and sign in with the operator token.
2. Choose **Pair a phone**. When the dashboard is opened at a non-local address, the code uses that same address.
3. Scan the code in the app, or type the address and key by hand.

The pairing code is JSON: `{"tollgate":1,"url":"https://gateway.example.com","key":"…"}`. A code that points at `127.0.0.1` is refused by the app, because on a phone that address is the phone itself.

## Agents against a deployed gateway

| Kind of agent | Works with a deployed gateway? |
| --- | --- |
| **Your own agent** (a program with its own key, using the [SDK](/sdk/) or the HTTP API) | Yes. Point it at the gateway's https address. |
| **Hosted chat agent** answered by the agent host | The agent host ships inside `pnpm live:app`, which starts its own gateway on your computer. Running it against a remote gateway is not packaged as its own command yet. |

So for a deployment today, use agents that bring their own key, or run `pnpm live:app` on the machine that should host the chat agents.

## Things that matter on a real host

- **Keep the gateway close to its database.** Every request makes several database calls. Across an ocean, each call costs a round trip, and chat feels slow. Put them in the same region.
- **Sleeping hosts.** Free tiers often stop a service after a quiet spell and take about a minute to wake. The first request after that is slow, and a payment can expire while it waits.
- **Secrets.** `GATEWAY_OPERATOR_TOKEN`, `SIGNER_SERVICE_TOKEN`, `DATABASE_URL` and the key file are secrets. Pass them through your host's secret store. Never commit `.env`.
- **The key file.** Upload it as a secret file and copy it to a private location with mode `600` before starting, as `render.yaml` does.
- **Rotating the owner's token.** Set a new `GATEWAY_OPERATOR_TOKEN` and restart. Every phone and dashboard must sign in again.
- **Rate limiting** is not built. Put it at your proxy if the gateway is on the open internet.
- **Backups** are your database's job. The audit chain is in the database, so a restore restores the chain.
- **Floats.** Fund the signer with what you can afford to lose, not with the budget you plan to give agents. See [Going live](/going-live/).

## A checklist before you expose it

1. `GATEWAY_OPERATOR_TOKEN` is long, random and secret.
2. https works, and `http://` is not reachable from outside.
3. `GET /healthz` returns `{"ok":true,"frozen":false}`.
4. The signer port is **not** reachable from outside the machine.
5. `TOLLGATE_OFFLINE` is what you intend.
6. A test payment with a tiny budget goes through the whole flow, including an approval from the phone.
7. You know how to freeze: the kill switch in the dashboard or the phone, or `POST /v1/freeze`.
